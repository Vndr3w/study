# Домашнее задание к занятию «Компоненты Kubernetes» - Лукинов Андрей

<details>
<summary><b>Задание. Необходимо определить требуемые ресурсы</b></summary>

Известно, что проекту нужны база данных, система кеширования, а само приложение состоит из бекенда и фронтенда. Опишите, какие ресурсы нужны, если известно:

1. Необходимо упаковать приложение в чарт для деплоя в разные окружения. 
2. База данных должна быть отказоустойчивой. Потребляет 4 ГБ ОЗУ в работе, 1 ядро. 3 копии. 
3. Кеш должен быть отказоустойчивый. Потребляет 4 ГБ ОЗУ в работе, 1 ядро. 3 копии. 
4. Фронтенд обрабатывает внешние запросы быстро, отдавая статику. Потребляет не более 50 МБ ОЗУ на каждый экземпляр, 0.2 ядра. 5 копий. 
5. Бекенд потребляет 600 МБ ОЗУ и по 1 ядру на копию. 10 копий.

<details>
<summary><b>Ответ</b></summary>

1. Расчёт ресурсов для приложения

    Сначала посчитаем суммарные запросы для всех компонентов в одном экземпляре окружения.

    | Компонент          | Реплик | CPU на реплику | RAM на реплику | Итого CPU | Итого RAM |
    | :----------------- | :----- | :------------- | :------------- | :-------- | :-------- |
    | База данных        | 3      | 1 ядро         | 4 ГБ           | 3 ядра    | 12 ГБ     |
    | Кеш                | 3      | 1 ядро         | 4 ГБ           | 3 ядра    | 12 ГБ     |
    | Фронтенд           | 5      | 0.2 ядра       | 50 МБ          | 1 ядро    | 250 МБ    |
    | Бекенд             | 10     | 1 ядро         | 600 МБ         | 10 ядер   | 6 ГБ      |
    | Итого для нагрузки |        |                |                | 17 ядер   | 30.25 ГБ  |

2. Служебные ресурсы и накладные расходы

    На каждой рабочей ноде, помимо пользовательских подов, работают системные компоненты Kubernetes (kubelet, kube-proxy, container runtime) и демоны ОС. Для стабильности необходимо зарезервировать часть ресурсов.

    В документации Kubernetes и облачных провайдеров рекомендуется явно задавать system-reserved и kube-reserved. Типичные значения для ноды с 8–16 ГБ RAM:

    - CPU: ~100–500 millicores

    - Память: ~100–1000 MiB

    Для расчёта примем консервативный запас на служебные нужды: 0.5 ядра CPU и 1 ГБ RAM на каждую ноду. Это покрывает системные демоны и kubelet.

3. Определение количества и размера рабочих нод

    **3.1. Требования к отказоустойчивости**

    - Запас на отказ минимум одной ноды. Кластер должен продолжать работать при выходе из строя любой одной рабочей ноды. Это означает, что суммарной ёмкости оставшихся нод должно хватать для размещения всех подов.

    - Для etcd (если используется встроенный) рекомендуется нечётное количество нод (3, 5), но в задании речь идёт о рабочих нодах для нагрузки. Отказоустойчивость etcd обычно обеспечивается на управляющих нодах, которые в расчёт рабочих не входят.

    **3.2. Выбор стратегии: несколько небольших нод vs одна большая**

    ***Вариант A: ноды среднего размера (например, 8 vCPU / 32 ГБ RAM)***

    Это компромиссный вариант: достаточно ресурсов для плотной упаковки подов, но отказ одной ноды не приведёт к потере слишком большой доли ёмкости.

    Расчёт полезной ёмкости одной ноды (8 vCPU / 32 ГБ):

    - Служебные ресурсы: −0.5 CPU, −1 ГБ RAM

    - Доступно для подов: 7.5 vCPU, 31 ГБ RAM

    Сколько нод нужно для размещения нагрузки (17 CPU, 30.25 ГБ)?

    - По CPU: 17 / 7.5 ≈ 2.27 → минимум 3 ноды

    - По RAM: 30.25 / 31 ≈ 0.98 → минимум 1 нода

    С учётом отказа одной ноды:
    Если одна нода выходит из строя, оставшиеся должны выдержать всю нагрузку. При 3 нодах после отказа остаётся 2 ноды с суммарной доступной ёмкостью 2 × 7.5 = 15 vCPU и 2 × 31 = 62 ГБ RAM. Этого недостаточно по CPU (нужно 17). Поэтому 3 нод мало.

    Добавляем ещё одну ноду: 4 ноды по 8 vCPU / 32 ГБ.

    - Суммарная доступная ёмкость: 4 × 7.5 = 30 vCPU, 4 × 31 = 124 ГБ RAM.

    - При отказе одной ноды остаётся: 3 × 7.5 = 22.5 vCPU, 3 × 31 = 93 ГБ RAM — этого достаточно для 17 CPU и 30.25 ГБ.

    - Запас: по CPU (22.5 − 17) / 17 ≈ 32%, по RAM (93 − 30.25) / 30.25 ≈ 207% (очень большой, но RAM не является узким местом).

    Этот вариант проходит, но RAM используется неэффективно.

    ***Вариант B: более компактные ноды (например, 4 vCPU / 16 ГБ RAM)***

    Полезная ёмкость одной ноды (4 vCPU / 16 ГБ):

    - Служебные: −0.5 CPU, −1 ГБ RAM

    - Доступно: 3.5 vCPU, 15 ГБ RAM

    Минимум нод для нагрузки:

    - По CPU: 17 / 3.5 ≈ 4.86 → 5 нод

    - По RAM: 30.25 / 15 ≈ 2.02 → 3 ноды

    - Определяющий фактор — CPU, нужно 5 нод.

    С учётом отказа одной ноды:
    При 5 нодах после отказа остаётся 4 ноды: 4 × 3.5 = 14 vCPU — недостаточно (нужно 17).
    Добавляем ещё: 6 нод по 4 vCPU / 16 ГБ.

    - Суммарно доступно: 6 × 3.5 = 21 vCPU, 6 × 15 = 90 ГБ RAM.

    - При отказе одной: 5 × 3.5 = 17.5 vCPU, 5 × 15 = 75 ГБ RAM — ровно столько, сколько нужно (17 CPU). Запас по CPU всего ~3%, что рискованно.

    - Лучше взять 7 нод: при отказе остаётся 6 × 3.5 = 21 vCPU, запас ~23%. Это уже надёжно.

    Итог по варианту B: 7 нод × (4 vCPU, 16 ГБ RAM) — проходит, но требует больше нод, что увеличивает накладные расходы на управление.
    Вариант C: крупные ноды (например, 16 vCPU / 64 ГБ RAM)

    Полезная ёмкость одной ноды: 15.5 vCPU, 63 ГБ RAM.

    - Минимум для нагрузки: 17 / 15.5 ≈ 1.1 → 2 ноды.

    - С учётом отказа одной ноды: при 2 нодах отказ одной оставляет 15.5 vCPU — меньше 17. Не проходит.

    - 3 ноды по 16 vCPU / 64 ГБ: суммарно 46.5 vCPU. При отказе одной остаётся 31 vCPU — с большим запасом. RAM избыточна.

    Этот вариант даёт большой запас, но может быть дороже.

4. Рекомендуемое решение

    С учётом баланса между стоимостью, управляемостью и отказоустойчивостью, оптимальным выглядит вариант с 4 нодами по 8 vCPU и 32 ГБ RAM.

    Параметры одной рабочей ноды:

    - vCPU: 8

    - RAM: 32 ГБ

    - Служебный резерв: 0.5 vCPU, 1 ГБ RAM (настраивается через system-reserved и kube-reserved)

    - Доступно для подов: 7.5 vCPU, 31 ГБ RAM

    Количество нод: 4

    Проверка отказоустойчивости:

    - Суммарная ёмкость для подов: 4 × 7.5 = 30 vCPU, 4 × 31 = 124 ГБ RAM.

    - При отказе одной ноды остаётся: 3 × 7.5 = 22.5 vCPU, 3 × 31 = 93 ГБ RAM.

    - Требуется: 17 vCPU, 30.25 ГБ RAM.

    - Запас после отказа: по CPU ~32%, по RAM ~207%. По CPU запас достаточный, по RAM — с избытком (можно использовать более дешёвые ноды с меньшим объёмом RAM, если это возможно).

5. Управляющие ноды (control plane)

    Для отказоустойчивого кластера рекомендуется 3 управляющие ноды (etcd требует кворума). Их ресурсы обычно невелики: 2 vCPU и 4–8 ГБ RAM на ноду. В расчёт рабочих нод они не входят, но должны быть учтены в инфраструктуре.

    Рекомендация: 3 control-plane ноды по 2 vCPU / 4 ГБ RAM (минимум).
